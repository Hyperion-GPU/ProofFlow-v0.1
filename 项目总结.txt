我们正在设计并开发一个叫 ProofFlow 的本地优先 AI 工作流仪表盘。

项目 GitHub：

https://github.com/Hyperion-GPU/ProofFlow-v0.1
1. 项目起源

最开始的想法是找一个“一个人 + Codex/AI agent 能做出来，但又真的有实用价值”的项目。

最初讨论过几个方向：

AgentGuard：AI 写代码后的验收门禁
LocalProof：本地文件证据管家
引用优先知识库搜索器
设备/工控日志异常解释器
个人项目决策记录器
图片/模型素材资产库
ComfyUI 图像工作流控制台

后来把这些方向合并成一个更统一的产品：

ProofFlow：一个 local-first 的 AI 工作流仪表盘，把代码、文件、日志、文档、图像资产、项目决策都变成可追踪、可引用、可回滚、可导出的工作流证据链。

它不是普通 AI chat app，也不是普通文件管理器，而是一个：

AI 工作流黑匣子 + 证据包生成器 + 本地操作控制台。

2. 核心产品目标

ProofFlow 要解决的问题是：

现在 Codex、Claude Code、Cursor 这类 AI agent 越来越能帮人写代码、整理文件、分析日志、处理文档、生成图像，但问题是：

AI 做了什么？
为什么这么做？
依据是什么？
有没有风险？
改动能不能验收？
文件操作能不能回滚？
决策以后还能不能追溯？

ProofFlow 的目标就是把这些工作流变成有证据链的 Case。

一句话定位：

ProofFlow 是一个本地优先的 AI 工作流仪表盘，帮助个人开发者和小团队把 AI/脚本/人工操作变成可验证、可审计、可回滚、可导出的 Proof Packet。

3. 核心抽象：Evidence Graph

ProofFlow 不应该被设计成一堆散装功能 tab，而应该围绕统一数据模型。

核心对象：

Case       一次工作流事件包
Artifact   文件、代码 diff、日志、图片、PDF、测试输出等证据对象
Run        一次脚本/测试/AI/扫描运行记录
Claim      AI 或系统给出的判断
Evidence   支撑 Claim 的证据
Action     可执行操作，例如移动文件、重命名、导出报告
Decision   人最终做出的决策
Report     导出的 Proof Packet

所有模块都应该变成 Case：

AgentGuard        = code_review Case
LocalProof        = file_cleanup Case
知识库问答         = knowledge_answer Case
日志异常解释       = log_incident Case
图像工作流         = image_workflow Case
项目决策记录       = project_decision Case

一个 Case 的结构：

Case
├── Timeline
├── Artifacts
├── Runs
├── Claims
├── Evidence
├── Actions
├── Decisions
└── Proof Packet
4. 项目核心原则

这些是 ProofFlow 的产品不变量，应该写进 AGENTS.md，也应该贯穿所有代码设计：

No Case, no workflow.
No Evidence, no trusted Claim.
No Preview, no Action.
No Undo, no destructive Action.
No Test, no accepted code workflow.
No Source, no Artifact.

中文理解：

没有 Case，就不算一个工作流。
没有 Evidence，Claim 只能是草稿，不能被信任。
没有 Preview，就不能执行 Action。
没有 Undo，就不能执行危险操作。
没有测试，就不能接受代码工作流。
没有来源，就不能登记 Artifact。

特别重要的是：

ProofFlow 不是让 AI 更大胆地乱做事，而是给 AI 工作流加刹车、记录仪、验收门禁和证据链。

3. AgentGuard 对 untracked files 的摄入太宽

当前 AgentGuard 默认 include untracked files，并且可能把 untracked 文本文件完整读入 diff artifact。

风险：

巨大文件进入 SQLite / Proof Packet
.env / .pem / .key / .db / .sqlite 这类敏感文件被摄入

需要加：

敏感文件 denylist
单文件大小 cap，例如 256 KiB
超过 cap 的只记录 metadata，不记录全文
敏感 untracked 文件直接 skip，不读内容
记录 skipped/truncated metadata 或 claim

建议规则：

skip names:
- .env
- .env.local
- .env.production

skip suffixes:
- .pem
- .key
- .p12
- .pfx
- .db
- .sqlite
- .sqlite3
P2 问题
4. LocalProof suggestions 可能生成不可执行的 move actions

从 ProofFlow 原则看，更推荐方案 A：

4. Legacy undo guard sanity check

我们补了 legacy executed move_file / rename_file 的安全回归：

- init_db() 做 legacy hash guard 回填时，如果旧文件已删除、不可读或 hash 读取失败，不会导致应用启动崩溃。
- migration failure 会记录 hash_guard_migration_failed 和 hash_guard_migration_error。
- 不会伪造 from_sha256 / source_sha256。
- undo 阶段如果缺少可信 hash guard，会返回可恢复的 400 错误，而不是 500。

这一步保证旧数据库升级失败时仍然保留 action 记录，并且不会把不可信的 legacy action 标记成安全。

Phase 2 关键行为：

- Preview 只读，不创建 backup directory、archive、manifest、Case、Artifact、Evidence 或 DB row。
- Create 使用 sqlite3.Connection.backup() 做 SQLite consistent snapshot，不 raw-copy live DB。
- Archive 是 ZIP。

Phase 3 preview 行为：

- 要求 backup 存在。
- 要求 backup status 是 verified。
- 调用只读 integrity helper，重新校验 manifest hash、archive hash、ZIP members 和 file hashes。
- 不比较 archive contents against current live source files。
- 校验 manifest app_version 和 schema_version。

- manifest 缺 app_version 或 schema_version 会阻断 restore trust。
- 拒绝 target_db_path 等于当前 live PROOFFLOW_DB_PATH。
- 拒绝 target_data_dir 等于当前 live PROOFFLOW_DATA_DIR。
- 拒绝 target 位于 live data_dir / proof_packets 内或与 live managed roots 重叠。
- 把 archive member 映射为 planned_writes：
  - db/proofflow.db -> target_db_path
  - data/<relative> -> target_data_dir/<relative>
  - proof_packets/<relative> -> target_data_dir/proof_packets/<relative>
- planned_writes 包含 archive_relative_path、target_path、role、action、size_bytes、sha256、would_overwrite。
- 计算 deterministic plan_hash。
- 持久化 restore_previews row。
- 记录 restore_preview Evidence。
- 不创建 trusted restore Claim。

注意：

用户给出的 Phase 3 contract 明确允许 preview 持久化 restore_previews row，以 enforce “No Preview, no Restore”。
因此 preview 会写 ProofFlow metadata DB，但不会创建任何 target files 或 target directories。

Phase 3 restore-to-new-location 行为：

- 要求 backup 存在且 verified。
- 要求 accepted_preview_id。
- 加载 restore_previews row。
- 校验 preview.backup_id 与 request.backup_id 一致。
- 校验 preview.target_db_path / target_data_dir 与 request resolved path 一致。
- 重新校验 manifest hash、archive hash、ZIP members、file hashes。
- 重新计算 current restore plan。
- current plan_hash 必须等于 preview.plan_hash。
- 如果 target filesystem state 在 preview 后变化，会拒绝并要求重新 preview。
- 如果 archive/manifest 在 preview 后变化，会拒绝并要求重新 verify + preview。
- 如果任何 planned write 会 overwrite existing target file/directory，会拒绝。
- 不写当前 live DB/data/proof_packets。
- 不使用 ZipFile.extract() 或 extractall()。
- 只读取 manifest-listed ZIP members 并手动 write_bytes 到目标。
- 拒绝 zip-slip：
  - absolute paths
  - Windows drive paths
  - backslash traversal
  - ..
  - empty components
- unexpected ZIP member 会让只读 integrity check 失败，restore 不会写。
- failed restore write 会尽量清理本次创建的 files/directories。
- restore result Evidence 记录失败时会降级成 response warning，不让已经完成的新位置 restore 变成半成功 API error。

### Policy Gate Enforcement 核心实现

高风险动作（move_file, rename_file）在 execute 时：

1. `evaluate_policy_gate()` 调用 classifier → 判定 high-risk
2. 状态转为 `pending_decision`，文件不动
3. 前端显示 orange status pill + gate banner（categories + reason）
4. Owner 点击 "Approve & Resolve Gate" → 创建 Decision（绑定 action_id + pipeline_id + preview_hash）
5. 再次 execute → `_validate_decision_gate()` 验证 binding → 执行文件操作

安全语义：
- Fail-open：classifier/observer 崩溃 → 不阻塞，正常执行
- Fail-closed：一旦进入 pending_decision → 必须有 valid Decision 才能继续
- Decision binding：必须匹配 action_id + policy_evaluation_id + preview_hash

关键文件：
- `backend/proofflow/services/action_service.py` — `_check_policy_gate()`, `_validate_decision_gate()`
- `backend/proofflow/services/policy_gate_runtime_observer.py` — `evaluate_policy_gate()`, `PolicyGateEnforcementResult`
- `backend/tests/conftest.py` — autouse fixture bypass gate for non-enforcement tests
- `frontend/src/pages/CaseDetail.tsx` — `PolicyGateBanner` component
- `frontend/src/pages/LocalProof.tsx` — same gate UI

   - 市面上没有"AI agent 操作审计 + 证据链"的 MCP server

   - ProofFlow 的定位是"AI 工作流黑匣子"，天然适合作为 MCP tool 嵌入
